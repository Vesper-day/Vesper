# IOS_ALARM_REBUILD

**Trigger:** The generated iOS project was wiped — typically by `expo prebuild --clean` — or an iOS/Xcode SDK update requires re-adding the native alarm extension. Native iOS directories (`apps/mobile/ios/` build artifacts) are NOT committed; only the hand-authored extension sources under `apps/mobile/ios/VesperAlarmExtension/` are version-controlled and must be re-wired into a freshly generated Xcode project.
**Frequency:** On-demand (after every `expo prebuild --clean`, SDK bump, or native rebuild).
**Owner:** Founder (V1).

> **This is the first expo-prebuild rebuild runbook.** It is the canonical pattern for re-attaching a hand-authored native target after prebuild regenerates `ios/`. (The widget runbook IOS_WIDGET_REBUILD.md, Chat 077, is forward-looking and not yet authored.)

> **macOS / Xcode required.** Every step in the Procedure runs on a Mac with Xcode. None of it is runnable on Windows. On-device verification and the time-sensitive entitlement are additionally gated on **Apple Developer enrollment (C-04), which is incomplete** — until C-04 lands, build to a development device is limited and the time-sensitive interruption level will not take effect.

## Committed source inventory

These files are committed and are the inputs to this runbook. After `expo prebuild --clean` they are NOT auto-added to the Xcode project — you re-attach them in the steps below.

| File | Role |
|---|---|
| `apps/mobile/ios/VesperAlarmExtension/AlarmContentView.swift` | SwiftUI full-screen alarm surface (edge-to-edge SNOOZE/STOP visuals) |
| `apps/mobile/ios/VesperAlarmExtension/NotificationViewController.swift` | `UNNotificationContentExtension` principal class; stamps `fired_at` into the app group at display time |
| `apps/mobile/ios/VesperAlarmExtension/SharedAlarmStore.swift` | App-group id + hand-off keys (shared writer/reader contract) |
| `apps/mobile/ios/VesperAlarmExtension/Info.plist` | Extension Info.plist; `UNNotificationExtensionCategory = vesperalarm`, default-content-hidden, full-height ratio, principal-class (no storyboard) |
| `apps/mobile/ios/VesperAlarmExtension/VesperAlarmExtension.entitlements` | App group + `com.apple.developer.usernotifications.time-sensitive` |

RN-side counterparts (committed, no Xcode work needed): `apps/mobile/lib/alarm.ts`, `apps/mobile/lib/analytics.ts`. The main-app time-sensitive entitlement is declared in `apps/mobile/app.config.js`.

---

## Detection

This runbook is needed when any of the following is true:
- `apps/mobile/ios/` was just (re)generated by `expo prebuild` / `expo prebuild --clean`.
- The alarm fires as a plain banner with no full-screen UI and no SNOOZE/STOP buttons (category/extension not wired).
- `alarm_fired` analytics never arrive after an alarm displays (app-group hand-off not readable — bridge or entitlement missing).

---

## Procedure (DEFERRED TO A MAC SESSION — do not run on Windows)

> Each step below is **Mac/Xcode-only** and is intentionally not executed in the Windows authoring chat.

1. **[DEFERRED-TO-MAC] Generate the native project.** From `apps/mobile`, run `expo prebuild` (or `expo prebuild --clean` for a from-scratch regen). This recreates `apps/mobile/ios/` with the main app target only — the alarm extension is NOT included.

2. **[DEFERRED-TO-MAC] Add the extension target in Xcode.** Open `ios/Vesper.xcworkspace`. File → New → Target → **Notification Content Extension**. Name it `VesperAlarmExtension`, bundle id `com.vesper.app.VesperAlarmExtension`. Delete the template-generated `NotificationViewController.swift`, `Info.plist`, and `MainInterface.storyboard` that Xcode scaffolds.

3. **[DEFERRED-TO-MAC] Wire the committed SwiftUI/native files into the target.** Add `AlarmContentView.swift`, `NotificationViewController.swift`, and `SharedAlarmStore.swift` to the `VesperAlarmExtension` target (and `SharedAlarmStore.swift` ALSO to the main app target if/when the RN reader bridge links against it). Replace the scaffolded `Info.plist` with the committed one. Since the committed Info.plist uses a **principal class (no storyboard)**, set the target's principal class to `NotificationViewController` and remove any `NSExtensionMainStoryboard` reference.

4. **[DEFERRED-TO-MAC] Set the app group + entitlements.** On BOTH the main app target and `VesperAlarmExtension`: Signing & Capabilities → App Groups → add `group.com.vesper.app`. Point `VesperAlarmExtension`'s code-signing entitlements at the committed `VesperAlarmExtension.entitlements`. Confirm `com.apple.developer.usernotifications.time-sensitive` is present on the main app (from `app.config.js`) and on the extension.

5. **[DEFERRED-TO-MAC] Add the Push Notifications capability.** Add the **Push Notifications** capability to the main app target (required for the notification categories/interruption-level plumbing). Time-Sensitive notifications are enabled via the entitlement set in step 4.

6. **[DEFERRED-TO-MAC] Build the native RN bridge for the fired hand-off.** The RN reader `apps/mobile/lib/alarm.ts` (`getAlarmBridge()` → `consumeFiredHandoff()`) expects a native module `VesperAlarmBridge`. Add a small native module on the main app target that reads/clears the app-group UserDefaults via `SharedAlarmStore.consumeFiredHandoff()` and exposes it to RN. Until this exists the RN read no-ops (safe).

7. **[DEFERRED-TO-MAC] Build.** Select the Vesper scheme, build for a development device (`xcodebuild` / Xcode Run). Resolve any signing prompts.

8. **[DEFERRED-TO-MAC] On-device alarm-fire test.** On a physical device (lock-screen alarm cannot be validated on simulator): set a near-future `wakeTarget`, foreground the app once so `scheduleAlarm()` runs, lock the device, and confirm at fire time: (a) the full-screen alarm surface renders edge-to-edge; (b) SNOOZE and STOP appear and are tappable **without unlocking**; (c) SNOOZE re-arms ~9 min later; (d) STOP cancels; (e) on next foreground, `alarm_fired` is emitted with a plausible `latency_from_target_ms`. **Gated on Apple Developer enrollment (C-04).**

---

## Verification

The rebuild succeeds when:
- The alarm displays as a full-screen lock-screen surface (not a plain banner) with edge-to-edge SNOOZE/STOP.
- Both actions dismiss without unlock (`isAuthenticationRequired:false`).
- `alarm_scheduled`, `alarm_fired`, and `alarm_dismissed` events are emitted with the §11 payload shapes.
- App-group UserDefaults receives and is cleared of the `vesper.alarm.*` keys across an alarm cycle.

(Full on-device verification is blocked until C-04 / Apple Developer enrollment completes.)

## Rollback

If the rebuilt extension misbehaves, remove the `VesperAlarmExtension` target from the Xcode project and ship the main app without it: the alarm degrades to a standard local notification (no full-screen UI, no fired_at hand-off). The committed sources are unaffected; re-run this runbook to re-attach.
